Diving into CVE-2026-43284: Dirty Frag

August 24, 2026

01 - What is Dirty Frag? #

Dirty Frag is a Linux kernel vulnerability that chains two separate kernel bugs to gain root on an affected system. Each bug lives in an unrelated subsystem, and each one is individually blocked by conditions that commonly exist on real systems. However, because they share the same underlying memory-corruption pattern, they can be chained together — the first path is attempted, and if it is blocked, the exploit automatically falls back to the second. This means each variant covers the condition that would stop the other from working.

The two component vulnerabilities are:

  • xfrm-ESP Page-Cache Write — CVE-2026-43284, in the IPsec ESP input path. Merged to the netdev tree on 7 May 2026 and accepted into mainline on 8 May 2026 as commit f4c50a4034e6.
  • RxRPC Page-Cache Write — CVE-2026-43500, in the AFS RxRPC verify path. No patch exists in any tree at the time of disclosure.

02 - How Does Dirty Frag Happen? #

To understand Dirty Frag, it helps to first understand how Linux handles network packets. When a packet enters the kernel, it is stored in a structure called struct sk_buff, or SKB. Think of the SKB as a container that holds all information about a network packet as the kernel processes it.

Some packets are split into smaller pieces called fragments. The SKB tracks these using a field called frag, which holds a reference — a pointer — to the memory page where the fragment data lives, rather than a copy of that data.

The bug in both variants is a use-after-free on a page-cache reference. In the vulnerable paths, the kernel increments a reference count on a page to signal it is in use, but then releases that reference early — before it has finished working with the frag entry pointing to it. After the reference is dropped, the memory allocator is free to reuse that page for something else. However, the kernel still has the stale frag entry pointing to it and can write through it, corrupting whatever now occupies that page.

On its own this is already serious, but if the corrupted page happens to belong to a privileged file in the page cache — such as a setuid binary — the write lands directly on that file’s cached data. This is the primitive the exploit uses to escalate privileges.

The name Dirty Frag comes from what it targets: rather than corrupting the entire packet structure, the exploit focuses on the frag reference inside struct sk_buff.

03 - How Does it Differ from Copy Fail and Dirty Pipe? #

Dirty Frag, Copy Fail, and Dirty Pipe all follow the same underlying pattern: they abuse the kernel’s habit of sharing page-cache references rather than copying data. This is normally a performance optimisation — avoiding unnecessary copies makes the kernel faster. The problem is that when the kernel incorrectly handles one of these shared references, a write can land on the original memory rather than a private copy. This class of bug is sometimes called a page-cache write primitive.

The difference between the three vulnerabilities is which subsystem they exploit to reach that primitive:

  • Dirty Pipe (CVE-2022-0847) targets struct pipe_buffer. The Linux pipe subsystem passes data between processes by handing off page-cache references rather than copying the data. By manipulating the flags on a pipe buffer, Dirty Pipe tricks the kernel into treating a read-only page-cache reference as writable, allowing an attacker to overwrite the contents of files they should not be able to modify.
  • Copy Fail targets the AF_ALG cryptographic socket interface. When userspace passes data into an AF_ALG socket, the kernel is supposed to copy the data before operating on it. The bug allows this copy to be skipped under certain conditions, leaving the kernel working directly on the original page-cache page and making it writable.
  • Dirty Frag reaches the same primitive through the network packet path. The frag field inside struct sk_buff holds a reference to a page-cache page. The use-after-free described in section 02 allows the exploit to write through a stale frag reference to a page the kernel no longer considers in use, but which may now hold privileged data.

All three result in the same outcome: an attacker with no privileges can write to memory that should have been protected, including the content of files owned by root.

04 - Chaining the Exploits #

Dirty Frag has two exploitation paths: the xfrm-ESP variant and the RxRPC variant. Neither works everywhere on its own.

The xfrm-ESP variant requires the ability to create a new user namespace (unshare(CLONE_NEWUSER)). On systems such as certain Ubuntu configurations, this is blocked at the kernel level by security policies like AppArmor. When that restriction is in place, the xfrm-ESP path cannot proceed.

The RxRPC variant does not require user namespaces, but it depends on the rxrpc kernel module being loaded. This module is commonly absent on enterprise-focused distributions that do not ship or load AFS-related components. So while RxRPC can work where xfrm-ESP is blocked, it is not available on systems that do not have the module.

Rather than picking one path and failing silently when it is unavailable, Dirty Frag chains both variants. The exploit attempts xfrm-ESP first. If unshare() returns EPERM — the error code for a permission denial — the exploit recognises that this path is blocked and automatically falls back to RxRPC.

                    Dirty Frag
                         |
                 Try xfrm-ESP first
                         |
              +----------+----------+
              |                     |
            Works               EPERM (blocked)
              |                     |
              v                     v
        Continue with          Try RxRPC
        xfrm-ESP path               |
                                    |
                              +-----+-----+
                              |           |
                            Works       Fails
                              |           |
                              v           v
                         Continue       Exploit
                         with RxRPC     cannot proceed

The underlying vulnerability — the use-after-free on a frag page-cache reference — is the same in both paths. What changes is the kernel subsystem used to reach it. This is what makes the chain useful in practice: instead of relying on a single path that only works under specific conditions, the PoC checks the environment and selects whichever path is available.

06 - Detection and Mitigation #

Dirty Frag does not leave an obvious file or persistent artefact on disk. The most useful indicators are the unusual sequence of kernel operations performed during the attack.

Detection #

The two variants have different behaviours but both produce activity that is abnormal for regular applications.

The xfrm-ESP variant creates user and network namespaces, registers multiple XFRM security associations, and makes repeated splice() / vmsplice() calls targeting a setuid binary such as /usr/bin/su.

The RxRPC variant skips namespaces entirely. Instead it creates an AF_RXRPC socket, performs several add_key() calls to register RxRPC keys, and uses splice() to interact with sensitive files such as /etc/passwd or setuid binaries.

Individually some of these syscalls can appear in legitimate software. The detection signal is the combination and ordering of events. A process that opens an AF_RXRPC socket and immediately follows it with repeated splice() operations targeting a privileged file is highly suspicious.

Useful events to monitor include:

  • socket(AF_RXRPC, ...) from unexpected processes
  • unshare(CLONE_NEWUSER) immediately followed by XFRM socket activity
  • Repeated add_key("rxrpc", ...) calls
  • splice() or vmsplice() calls referencing setuid binaries or /etc/passwd
  • A process executing /usr/bin/su directly after any of the above

The goal is not to alert on every individual syscall in isolation, but to detect the chain of events that makes up the exploit sequence.

Mitigation #

The most effective mitigation is to update the kernel to a version that includes the relevant security patches. This removes the underlying vulnerability rather than attempting to detect exploitation in progress.

Until patched kernels are available, administrators can reduce the attack surface by disabling the kernel modules required by each path, where those modules are not in use. Note that this can affect legitimate services:

  • Disabling ESP-related modules will break IPsec.
  • Disabling rxrpc will affect systems that rely on AFS/RxRPC.

For production environments, the recommended approach is:

  1. Apply the vendor’s patched kernel as soon as it is available.
  2. Monitor for the suspicious syscall patterns described above.
  3. Disable unused vulnerable modules as an interim measure, after confirming no legitimate workloads depend on them.
  4. Verify that any module restrictions do not break existing IPsec or AFS/RxRPC services.

In short: patching removes the root cause, while behavioural monitoring buys time to detect exploitation attempts before they complete.
